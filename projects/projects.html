Brief explanation

In simple terms: Key interview topic: Fuse Logger — what problem, architecture, and impact. Multi-environment log search tool for Fuse/Camel integrations so engineers find errors by correlation ID without SSH to every server.

Brief explanation

Multi-environment log search tool for Fuse/Camel integrations so engineers find errors by correlation ID without SSH to every server.

Problem (detailed)

At Optima, production issues required grep across dev/test/prod servers. Average triage took 30–60 minutes. Senior engineers became bottlenecks. New joiners couldn't debug integration chains alone.

Solution architecture

  • UI: filters — env, time range, correlation ID, route name, log level, keyword
  • API: Spring Boot service — auth, query orchestration, pagination
  • Data: log aggregator (ELK / SSH tail / file agents — state your real stack)
  • Security: prod access only for authorized roles; audit who queried what

Technical challenges

  • Large log volume → time-bounded queries, max rows, async search
  • Consistent correlation ID across Camel hops — documented standard for teams

Impact

Lower MTTR, fewer escalations, daily use by integration team — strong "ownership beyond tickets" story.

Follow-ups

How handle PII in logs? How scale if QPS on search grows? → caching recent queries, read replicas on log store.

Why it was needed

Telecom identifiers (MIN, MSISDN, accountId) are confusing. Wrong manual SQL caused slow incidents and compliance risk.

Design details

  • Read-only DB user + connection pool limits + query timeout (e.g. 5s)
  • Input validation — reject wildcards that scan full table
  • Audit log: user, timestamp, ID searched

  • Optional: hit read replica not primary OLTP

MS-Builder — what is it, architecture, and impact?

Hard⭐ VIProject▼

📌 Revision keywords

  • OpenAPI → code
  • contract-first
  • templating
  • Docker + Jenkins generated
  • scaffolding

Brief explanation

In simple terms: MS-Builder is a tool that takes an OpenAPI spec and generates a ready-to-run Spring Boot microservice — controllers, Docker image, deploy config, and a Jenkins pipeline — so teams don't hand-write boilerplate for every new service.

Problem it solves

Every new microservice needed the same repetitive setup: project skeleton, REST controllers/DTOs, Dockerfile, deployment config, CI/CD pipeline. That was slow and inconsistent across teams.

Architecture (high level)

  1. Input: an OpenAPI (Swagger) spec — contract-first.
  2. Parser: reads paths, operations, and schemas into an internal model.
  3. Template engine: applies templates to emit Java code (@RestController, request/response models, service stubs).
  4. Infra generation: also emits a Dockerfile, deployment config, and a Jenkinsfile.
  5. Output: a complete, runnable service repo.

Impact

New services bootstrap in minutes instead of days, with a consistent structure and CI/CD out of the box — fewer setup mistakes, faster onboarding.

Why it's a strong interview project

Shows you understand contract-first API design, code generation, and the full path from spec → service → container → pipeline (exactly the DevOps maturity the ICE JD asks for).

MS-Builder — how does OpenAPI → Spring Boot generation work?

Hard⭐ VIProject▼

📌 Revision keywords

  • parse spec
  • model
  • templates (Mustache/Freemarker)
  • emit controllers + DTOs

Brief explanation

In simple terms: The spec describes the endpoints and data shapes; the builder parses that, then fills code templates to produce the matching Java classes.

The pipeline

  1. Parse the OpenAPI YAML/JSON (paths, operations, parameters, schemas).
  2. Build an internal model (each operation → a method; each schema → a DTO).
  3. Run the model through templates (e.g. Mustache/Freemarker) to emit controllers, models, and service interfaces.

Example — spec in

paths:
  /orders/{id}:
    get:
      operationId: getOrder
      responses:
        '200':
          content:
            application/json:
              schema:
                $ref: '#/components/schemas/Order'

Generated controller out

@RestController
public class OrdersApiController implements OrdersApi {
  @Override
  public ResponseEntity<Order> getOrder(String id) {
    // delegate to a service impl you fill in
  }
}

This is the same idea as the open-source OpenAPI Generator — I built a version tuned to our org's conventions (our Docker base image, Jenkins stages, package layout).

MS-Builder — design decisions & hardest challenges?

HardProject▼

📌 Revision keywords

  • regeneration vs custom code
  • template versioning
  • spec validation
  • build vs buy

Brief explanation

In simple terms: The tricky part of code generation is regenerating without wiping the business logic people added by hand.

Key challenges & how I handled them

  • Don't overwrite custom logic: separate generated code (interfaces/DTOs) from hand-written implementations, so re-running the generator is safe.
  • Spec validation: reject invalid OpenAPI early with clear errors, rather than emitting broken code.
  • Template versioning: templates evolve — version them so old services can regenerate predictably.
  • Consistency: enforce naming/package conventions so every generated service looks the same.

Build vs buy

OpenAPI Generator exists, but I needed our specific Docker base image, Jenkins stages, and deploy configs baked in — so a tailored builder gave a true one-click, org-standard service.

Likely follow-up

"What would you improve?" → plug in schema-compatibility checks, support gRPC/async (Kafka) templates, and a web UI to submit specs.
