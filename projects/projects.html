Brief explanation

In simple terms: Key interview topic: Fuse Logger — what problem, architecture, and impact. Multi-environment log search tool for Fuse/Camel integrations so engineers find errors by correlation ID without SSH to every server.

Brief explanation

Multi-environment log search tool for Fuse/Camel integrations so engineers find errors by correlation ID without SSH to every server.

Problem (detailed)

At Optima, production issues required grep across dev/test/prod servers. Average triage took 30–60 minutes. Senior engineers became bottlenecks. New joiners couldn't debug integration chains alone.

Solution architecture

  • UI: filters — env, time range, correlation ID, route name, log level, keyword
  • API: Spring Boot service — auth, query orchestration, pagination
  • Data: log aggregator (ELK / SSH tail / file agents — state your real stack)
  • Security: prod access only for authorized roles; audit who queried what

Technical challenges

  • Large log volume → time-bounded queries, max rows, async search
  • Consistent correlation ID across Camel hops — documented standard for teams

Impact

Lower MTTR, fewer escalations, daily use by integration team — strong "ownership beyond tickets" story.

Follow-ups

How handle PII in logs? How scale if QPS on search grows? → caching recent queries, read replicas on log store.

Subscriber Tool — safe production lookups by MIN / accountId

Medium⭐ VITool▼

📌 Revision keywords

  • SQL
  • Read
  • Input validation
  • PII masking in UI

Brief explanation

In simple terms: Key interview topic: Subscriber Tool — safe production lookups by MIN / accountId. Read-only tool for support/dev to fetch subscriber data by MIN or accountId without writing ad-hoc SQL on production.

Read-only tool for support/dev to fetch subscriber data by MIN or accountId without writing ad-hoc SQL on production.

Why it was needed

Telecom identifiers (MIN, MSISDN, accountId) are confusing. Wrong manual SQL caused slow incidents and compliance risk.

Design details

  • Read-only DB user + connection pool limits + query timeout (e.g. 5s)
  • Input validation — reject wildcards that scan full table
  • Audit log: user, timestamp, ID searched
  • PII masking in UI — partial phone, no full dump export by default
  • Optional: hit read replica not primary OLTP

Interview tip

Shows production maturity — "I think about safety, not only features."

Brief explanation

In simple terms: Key interview topic: SM Tool — deployment automation (deep dive). Orchestrates repeatable deploy steps for Fuse/Camel services — complements Jenkins; part of 60% manual effort reduction.

Orchestrates repeatable deploy steps for Fuse/Camel services — complements Jenkins; part of 60% manual effort reduction.

Before vs after

Before: manual JAR copy, config edit, restart, smoke check — 45+ min, error-prone. After: one workflow with checks and rollback.

Pipeline steps (example)

  1. Validate env + maintenance window
  2. Pre-check: disk, current version, running health
  3. Deploy artifact from Jenkins/Nexus
  4. Apply config from template per env
  5. Rolling restart / blue-green if available
  6. Post-deploy smoke: health URL + sample test transaction
  7. Auto-rollback on smoke failure

Hard topics

  • Idempotency: re-run deploy doesn't double-apply
  • Secrets: not in repo — vault or Jenkins credentials
  • Concurrency: lock so two deploys don't hit same env
